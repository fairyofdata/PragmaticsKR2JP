# 0002. 끌려가지 않기: 프롬프트 부탁 대신 코드 검증

- 상태: 채택 (2026-09-20)

## 맥락
이 앱의 존재 이유는 "뜻이 통해서 아무도 지적하지 않는 오류"를 잡는 것이다. LLM도 확률 모델이라
틀린 입력을 맞게 읽어버린다(`友達を合う` → 알아서 `友達に会う`로 이해). 실험(p0·p1)에서 관찰된 경로:
1. 오류 두 개를 태그 하나로 합쳐 하나가 묻힌다 (`を合→に会` 가 조사 태그 하나로).
2. 최소 교정에서는 넘기고 자연스러운 문장에서만 조용히 고친다 (`その→あの`).
3. 반대 방향: 반각 `!?` 같은 비오류를 오류로 지적한다(과교정).

프롬프트에 규칙을 넣어도("태그를 나눠라", "반각은 오류 아님") 모델은 안정적으로 따르지 않았다(3번 중 1번 / 거의 무시).

## 결정
지킬 수 있는 규칙은 코드로 옮긴다 (`coach/verify.py`, `coach/voting.py`).
- A. 입력 원문을 정규화 없이 저장.
- D. 태그 인용이 원문에 글자 그대로 있는지 검증 (없으면 버림).
- E. 원문→최소 교정의 바뀐 **글자 하나하나**가 태그로 덮였는지 검증. 인접한 두 수정이 diff에서 한 덩어리가 돼도 한 태그로 둘 다 덮은 것으로 치지 않는다 (테스트 작성 중 실제로 이 구멍을 발견).
- E2. 태그 하나에 "조사 + 다음 단어" 모양의 수정이 합쳐졌는지 검출 → 화면 경고. 다른 확정 태그가 이미 따로 지적했으면 경고하지 않음.
- 전각/반각만 다른 수정은 오류가 아님 (비교할 때만 NFKC, 저장은 원문 그대로).

## 버린 대안
- 프롬프트 규칙 강화만으로 해결: p1 실험에서 효과 없음.

## 결과 / 한계
- E2는 한 가지 모양만 잡는 좁은 규칙이다(`書け→かけ` 같은 한자→가나는 놓친다). 사용자의 예시 하나에 맞춘 규칙이라는 편향도 있다 → 형태소 분석기(SudachiPy)로 "태그 안에서 바뀐 단어 수"를 세는 방식으로 일반화 예정.
- 경로 2(자연스러운 문장에서만 조용히 고침)는 아직 막지 않았다.
- 실험 결과에 모델 원래 응답을 저장해, 검증 규칙을 바꾸면 API 없이 `--rescore` 로 다시 잴 수 있다.
