# PragmaticsKR2JP — 한국어 화자를 위한 일본어 작문 코치

[English](README.md) · 한국어 · [日本語](README_jp.md)

일본어로 쓴 짧은 글을 **고정된 오류 유형표**에 따라 태깅하고, 내가 자주 틀리는 유형을 코드로 집계해 보여주는 개인용 로컬 앱.

![연습 화면](docs/images/practice.png)

## 왜 만들었나

일본에서 일본어로 일하면 의사소통은 된다. 그런데 **뜻만 통하면 아무도 지적해 주지 않는다.**
`友達を合う`라고 써도 상대는 `友達に会う`로 알아듣고 넘어간다. 음성 인식은 더 심해서, 틀린 조사를 발음이 비슷한 맞는 조사로 "알아서" 바꿔 인식해 버린다.
그 결과 ほぼ/ほとんど/大体 를 구별 없이 쓰거나, 한국어를 그대로 옮긴 표현(`ストレスを受ける`, `薬を食べる`)이 몇 년이고 고쳐지지 않는다.

이 앱의 목표는 하나다: **틀린 것을 틀린 그대로 잡아서 보여주는 것.** 그리고 그것이 쌓여서 "내가 무엇을 반복해서 틀리는지"를 숫자로 보여주는 것.

## 설계 원칙

### 1. LLM은 주석자다. 측정의 나머지는 코드가 한다.

| LLM이 하는 일 | LLM에게 맡기지 않는 일 | 코드가 하는 일 |
|---|---|---|
| 과제 출제, 고정 유형표 안에서 오류 위치·유형 태깅, 교정문, 한국어 해설 | 점수, 수준 판정, 누적·순위·추세, 자기 결과의 검증 | 인용 검증, 미태깅 수정 검출, 다수결, 집계·순위, 일치율·탐지율 측정 |

- 수치 점수 대신 범주 태그만 받는다. LLM 판정자의 수치 점수는 잡음이 크고, 구체적 범주 판단이 더 안정적이라는 보고가 있다.
- 단, 오류 하나하나의 판단은 여전히 LLM이 하는 측정이다. "결정론적으로 집계했으니 객관적"이 아니다. 그래서 그 주석의 **재현성(신뢰도)과 탐지율(타당도)을 측정해 아래에 공개**한다.
- 기본은 유형표·프롬프트·스키마·모델 버전이 모두 현재와 같은 기록만 집계한다. 사이드바 토글로 유형표가 같은 이전 기록을 포함할 수 있고, 그때는 섞인 버전 구성을 화면에 보여준다. 유형표가 다르면 어떤 경우에도 섞지 않는다.

### 2. 끌려가지 않기

LLM도 음성 인식과 같은 확률 모델이라, 틀린 입력을 "아마 이런 뜻이겠지" 하고 맞게 읽어버린다. 이를 프롬프트 부탁이 아니라 **코드 검증**으로 막는다.

| | 장치 | 막는 것 |
|---|---|---|
| A | 입력 원문을 정규화 없이 저장 | 저장 단계에서 오류가 지워지는 것 |
| B | 해석(뜻)과 판정(오류)을 분리해서 출력 | "뜻이 통하니 됐다"며 넘어가는 것 |
| C | 최소 교정문 / 장면에 맞는 자연스러운 문장 분리. 화면의 교정문은 **확정 태그만 원문에 적용해 코드가 만든다** | 교정과 윤문이 섞여 오류가 흐려지는 것, 확정되지 않은 수정이 교정문에 섞이는 것 |
| D | **태그의 인용이 원문에 글자 그대로 있는지 코드가 검증.** 같은 글자(예: 「を」)가 여러 번 나오면 문맥 필드와 diff 로 위치를 코드가 정하고, 그래도 모호하면 경고 | 이미 고친 형태로 인용하는 것, 반복되는 조사의 오류 두 건이 하나로 합쳐지는 것 |
| E | **원문→교정문의 바뀐 글자가 모두 태그로 덮였는지 코드가 검증** | 조용한 교정 (화면에 경고로 표시) |
| F | 오류를 심은 평가 세트로 탐지율 측정 | "잘 잡는다"를 숫자로 확인 |

반대 방향 실패(과교정)도 측정한다: 오류 없는 답에 태그가 몇 개 붙는지.

일본어에 대한 지식은 [coach/lang_ja.py](coach/lang_ja.py) 한 곳에만 두고, 밖으로는 함수 두 개만 내보낸다. `tokenize_chunks`(SudachiPy가 있으면 형태소 분석, 없으면 표기 기반 근사)와 `non_error_diff` 다. [coach/verify.py](coach/verify.py), 다수결, 집계는 일본어를 전혀 모른다.

### 3. 흔들림은 다수결로

같은 답을 3번 채점해서, 같은 유형이고 위치가 겹치는 지적이 2번 이상 나온 것만 **확정**으로 집계한다. 1번만 나온 것은 "참고(낮은 확신)"로 화면에만 보여준다. 요약 화면에는 유형마다 전원 일치 건수와 낮은 확신으로 빠진 건수를 함께 보여준다. 합치는 것은 코드가 한다. 고정 few-shot 예시는 넣지 않는다(주제·유형 쏠림). 유형마다 과제와 무관한 짧은 대비쌍 1개만 둔다.

### 4. 모드 분리: 문법 / 표현

한 번에 판단할 유형 수를 줄여 재현성을 높이기 위해 두 모드로 나눈다. 모드 밖 오류는 `OUT_OF_MODE` 로만 표시하고 집계에서 뺀다.

| 문법 모드 (형태·통사: 정확성) | 공통 | 표현 모드 (어휘·화용: 적절성) |
|---|---|---|
| 조사 / 활용 / 시제·상 / 태·수수·자타동사 / 접속 | 표기·오타·변환 실수 / 기타 | 경어·정중체 / 문체·장면 적합성 / 문말 표현 / 어휘 선택 / 연어·관용 / 문장 구조·담화 |

모든 태그에는 `한국어 직역 간섭` 여부가 따로 붙는다. 과제에는 매체(메일/채팅/구두)와 관계(사외/상사/동료/친구)가 붙고, 판정은 그 장면 기준으로 한다.

## 재현성·탐지율 미니 실험

**방법** ([experiments/repro.py](experiments/repro.py))
- 평가 세트: 오류를 일부러 심은 답 12건 (문법 모드 6, 표현 모드 6, 그중 무오류 2건). 한국어 화자의 전형적 실수(`友達を合う`, `薬を食べる`, `ストレスを受ける`, `勉強しました時` 등)와 정답 위치를 함께 적었다.
- 세 조건을 각각 3번씩 채점: **plain**(유형 이름만 주는 단순 지시) / **guide**(상세 지침 프롬프트, 1회) / **vote**(상세 지침 + 3회 다수결).
- 모델 `gpt-5.6-terra` (reasoning effort = low). 1회 실험 = API 호출 180회.
- 지표는 모두 코드가 계산한다.

| 지표 | 뜻 |
|---|---|
| 완전일치 | 3번 채점의 유형 집합이 완전히 같은 답의 비율 (재현성) |
| Jaccard | 3번 중 두 개씩 비교한 유형 집합 겹침의 평균 (재현성) |
| 위치 탐지율 | 심은 오류 위치에 태그가 붙은 비율 — **끌려가지 않았는가** |
| 유형까지 일치 | 위치와 유형이 모두 맞은 비율 |
| 무오류 답의 태그 | 오류 없는 답에 붙은 태그 수 평균 — **과교정** |
| 기대 밖 태그 | 심은 위치 밖에 붙은 태그 수 평균 (진짜 오류일 수도 있음) |

**결과 1 — p0 (첫 프롬프트, 유형표 v0)** `experiments/results/repro_20260920_031543.json`

|---|---|---|---|---|---|---|---|
| plain | 문법 | 0.83 | 0.93 | 0.96 | 0.33 | 0.00 | 0.60 |
| plain | 표현 | 0.50 | 0.83 | 0.93 | 0.63 | 2.67 | 1.33 |
| guide | 문법 | 0.50 | 0.78 | 0.96 | 0.54 | 0.00 | 0.13 |
| guide | 표현 | 0.83 | 0.89 | 0.89 | 0.78 | 1.00 | 0.40 |

**p0 분석 → 고친 것**
1. `友達を合って`를 조사 태그 **하나로 합쳐** 한자 변환 실수(合→会)가 묻혔다 (3조건 모두). → 프롬프트에 "태그 하나에 오류 하나" 규칙 추가 (p1).
2. 반각 `!` `?` 를 표기 오류로 지적 → 무오류 답에 태그가 붙음. → 유형표에 "전각/반각 차이는 오류가 아니다" 명시.
3. `薬を食べる`를 COLLOCATION 이 아니라 WORD_CHOICE 로 태깅. 모델이 아니라 **유형표의 우선순위가 잘못**이었다. → 더 구체적인 COLLOCATION 을 위로 (유형표 v1).
4. 평가 세트 E4(`先週一緒に行ったその店`)는 수식절이 붙어 その도 자연스럽다. **정답 라벨 오류**였다. → 문항 교체.

**결과 2 — p1 (프롬프트 p1, 유형표 v1, E4 교체)** `experiments/results/repro_20260920_032338.json`

| 조건 | 모드 | 완전일치 | Jaccard | 위치 탐지율 | 유형까지 일치 | 무오류 답의 태그 | 기대 밖 태그 |
|---|---|---|---|---|---|---|---|
| plain | 문법 | 0.67 | 0.83 | 1.00 | 0.29 | 0.00 | 0.60 |
| plain | 표현 | 0.17 | 0.67 | 0.93 | 0.67 | 2.33 | 0.80 |
| guide | 문법 | 0.67 | 0.86 | **1.00** | 0.62 | 0.00 | 0.07 |
| guide | 표현 | 0.50 | 0.69 | 0.81 | 0.78 | 0.67 | 0.13 |
| vote | 문법 | 0.67 | 0.85 | **1.00** | 0.58 | 0.00 | 0.07 |
| vote | 표현 | 0.67 | 0.82 | 0.74 | 0.67 | 1.00 | 0.20 |

**p1 분석**
- **프롬프트 규칙은 지켜지지 않았다.** "태그를 나눠라"는 3번 중 1번만 지켰고, "반각은 오류 아님"은 거의 무시했다. → 두 규칙을 **코드 검증으로 옮겼다** (아래 E2, 전각/반각 필터). 이 프로젝트의 원칙("부탁하지 말고 코드로 막는다")을 실험이 뒷받침한 셈이다.
- 새 E4(`ねえ、その店覚えてる？` → あの)는 3조건 모두 태그 0건. 그런데 natural_version 에서는 あの 로 고쳐 썼다. **최소 교정에서는 넘기고 자연스러운 문장에서만 조용히 고치는** 또 다른 끌려가기 경로다(다음 단계에서 다룸). 다만 後方照応의 その 로 볼 여지도 있어 라벨 자체도 원어민 검수가 필요하다.

**p1 이후 추가한 코드 검증** (API 재호출 없이 `--rescore` 로 저장된 응답에 다시 적용 가능)
- E2 합침 검출: 태그 하나 안에서 **서로 다른 단어가 2개 이상** 고쳐졌으면 화면에 경고. 단어 나누기는 형태소 분석기(SudachiPy)가 하고, 없으면 표기 기반 근사로 돌아간다. 오쿠리가나(`食べ→飲ん`)나 경어 삽입(`連絡→ご連絡`)은 한 단어 안의 일이라 경고하지 않는다.
- 전각/반각 차이만 있는 수정은 태그와 누락 검증 모두에서 제외. 단 **문장부호·공백·숫자·영문에 한정**한다. 반각 가타카나(`ｻｰﾊﾞｰ→サーバー`)는 실제 표기 오류이므로 남긴다.
- 이 두 규칙은 위 표를 측정한 뒤에 일반화했다. 표의 숫자는 일반화 이전 코드 기준이며, 당시 결과 파일에는 모델의 원래 응답이 없어 다시 계산할 수 없다(원래 응답 저장은 그 뒤에 추가). 다음 실험부터는 `--rescore` 로 API 없이 다시 잴 수 있다.

**현재 상태:** 앱은 프롬프트 p2 · 스키마 s2 로 동작한다 (반복되는 인용의 위치 결정, 확정 태그로 만든 교정문 — [ADR 0009](docs/adr/0009-quote-resolution-version-filter.md)). 실제 API 동작 확인은 1건으로 마쳤고, p2 본 실험은 평가 세트를 실제 번역으로 다시 만든 뒤로 보류한다 ([ADR 0007](docs/adr/0007-eval-set-from-user-translations.md)). 아래 비용은 p1 실측이며, p2 확인에서는 채점 1번에 약 $0.04 였다 (문맥 필드와 추론 토큰 증가).

**결론 (문항 12개라는 작은 표본 기준)**
1. **문법 모드는 끌려가지 않는다**: p1 에서 guide·vote 모두 심은 오류 위치를 전부 잡았다 (1.00). p0 에서는 guide 0.96, vote 1.00. 표현 모드는 p1 에서 plain 0.93 / guide 0.81 / vote 0.74 로 문법 모드보다 낮고, 지침을 넣을수록 오히려 낮아졌다 (기대 밖 태그가 줄어든 대가로 보인다). LLM이 표면 교정에 강하고 화용에 약하다는 선행 연구와 같은 방향.
2. **상세 지침 프롬프트는 확실히 낫다** (한 실행 안의 비교, 전체 기준): p1 에서 plain → guide 로 유형 일치 0.49 → 0.71, 기대 밖 태그 0.70 → 0.10, 무오류 답의 태그 1.17 → 0.33. p0 에서도 같은 방향 (0.49 → 0.67, 0.97 → 0.27, 1.33 → 0.50).
3. **3회 다수결의 효과는 이 표본으로는 판단할 수 없다.** 0.1 정도의 차이는 문항 12개에서는 잡음 범위다. 그래도 태그마다 "3번 중 몇 번"이라는 확신도를 주므로 기본값으로 유지한다.
4. **재현성은 아직 낮다** (완전일치 0.5~0.67). 흔들림은 주로 유형 경계(REGISTER↔POLITENESS, CONNECTIVE↔TENSE_ASPECT)에서 난다. 위치는 안정적이고 유형 이름이 흔들린다.

**한계**
- 평가 세트는 Claude 가 쓰고 GPT 가 채점했다. 모델은 다르지만 **사람이 만든 정답이 아니다.** 실제로 라벨 오류 1건을 실험으로 발견했다. 일본어 원어민의 정답 검수가 가장 싼 개선이다.
- 요약 화면의 "상위 5개"는 "받은 과제에서 자주 틀린 유형"이다. 주제마다 유발하는 오류가 다르다.
- G2(`担当するので`)처럼 문법 문제(시제·상)로도, 표현 문제(ことになる)로도 볼 수 있는 문항은 모드 경계에서 판단이 갈린다.

## 실행 방법

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
copy .env.example .env        # OPENAI_API_KEY (또는 GEMINI_API_KEY + LLM_PROVIDER=gemini) 입력
.venv\Scripts\streamlit run app.py
```

- 연습 탭: 사이드바에서 모드·주제 선택 → 과제 받기 → 일본어로 쓰기 → 채점
- 요약 탭: 모드별 "자주 틀리는 유형 상위 5개"와 실제 예시. 시연용 예시(`samples/`)와 내 기록(`data/`)을 골라 볼 수 있다.
- 연속 사용일 표시는 사이드바에서 켤 수 있다(기본 꺼짐). 할당량이나 목표 점수는 없다.
- 동봉된 시연 예시는 프롬프트 p1 로 만든 것이라, 기본(엄격) 버전 필터에서는 요약에 나오지 않는다. 사이드바의 **"이전 버전 기록도 포함"** 을 켜면 보인다.

테스트와 실험:

```powershell
.venv\Scripts\python -m pytest -q                    # LLM 없이 검증·다수결·집계 테스트
.venv\Scripts\python -m experiments.repro            # 재현성·탐지율 실험 (API 호출 약 180회)
.venv\Scripts\python -m experiments.build_samples    # 시연용 예시 재생성
.venv\Scripts\python -m tools.screenshots            # README 스크린샷 재생성
```

## 다음 단계

이번 범위(연휴 MVP)에서 뺀 것과, 실험에서 나온 개선 과제.

**끌려가지 않기 강화**
- natural_version 에서만 조용히 고친 곳(예: その→あの)을 드러내기 — 최소 교정과 자연스러운 문장의 차이를 "참고 표현"으로 보여주는 방식 검토
- 평가 세트를 원어민이 검수하고 30건 이상으로 늘리기 (지금은 0.1 차이를 구별할 수 없음)
- 음성 입력: 언어 모델 보정 없이 가나 단위로 인식하는 방식이어야 이 앱의 목적과 맞는다

**기능**
- 음성 입력, 정기 시험, 복습 스케줄러, 차트 여러 개, 로그인, 배포 (이번 범위 밖)
- 기록이 쌓이면 "같은 유형의 과거 사례"를 찾아 예시로 넣는 동적 few-shot
- 사내 Copilot 에 했던 일본어 질문을 `source: "imported"` 로 가져오기
