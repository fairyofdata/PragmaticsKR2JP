# PragmaticsKR2JP — 韓国語母語話者のための日本語ライティング・コーチ

[English](README.md) · [한국어](README_kr.md) · 日本語

自分が書いた日本語を**固定の誤用分類表**に従ってタグ付けし、「何を繰り返し間違えているか」を**コードで**集計する個人用ローカルアプリです。集計や順位付けは LLM にはさせません。

![練習画面](docs/images/practice.png)

## なぜ作ったか

日本で日本語で働いていると、意思疎通はできます。しかし**意味が通じてしまう限り、誰も直してくれません。**
`友達を合う` と書いても、相手は `友達に会う` と受け取って流します。音声認識はもっと厄介で、間違った助詞を発音の近い正しい助詞へ勝手に「直して」しまうため、間違いに気づく機会そのものが失われます。
その結果、ほぼ / ほとんど / 大体 を区別せずに使い続けたり、韓国語をそのまま移した言い方（`ストレスを受ける`、`薬を食べる`）が何年も残ったりします。

目的はひとつです。**間違いを間違いのまま捉えて見せること。** そしてそれを積み上げて、繰り返す弱点を数字で示すことです。

## 設計方針

### 1. LLM は注釈者。測定の残りはコードが行う

| LLM がやること | LLM に任せないこと | コードがやること |
|---|---|---|
| 課題の出題、固定分類表内での誤用箇所・種別のタグ付け、添削文、韓国語の解説 | 点数、レベル判定、累計・順位・傾向、自分の出力の検証 | 引用の検証、タグなし修正の検出、多数決、集計と順位付け、一致率・検出率の測定 |

- 数値の点数ではなく範疇タグだけを受け取ります。LLM 判定者は自由な数値尺度では揺れが大きく、具体的な範疇判断のほうが安定するという報告があるためです。
- ただし誤用一つひとつの判断は、やはり LLM による測定です。「決定的に集計したから客観的」とは言えません。そこで注釈の信頼性（再現性）と妥当性（検出率）を測り、下に公開しています。
- 既定では、分類表・プロンプト・スキーマ・モデルのバージョンがすべて現在と同じ記録だけを集計します。サイドバーの切り替えで分類表が同じ以前の記録を含めることができ、その場合は混在したバージョン構成を画面に表示します。分類表が異なる記録は決して混ぜません。

### 2. 引きずられない

LLM も音声認識と同じ確率モデルで、誤った入力を「たぶんこういう意味だろう」と正しく読んでしまいます。これをプロンプトでのお願いではなく、**コードの検証**で防ぎます。

| | 仕組み | 防ぐもの |
|---|---|---|
| A | 入力を正規化せずそのまま保存 | 保存の段階で誤用が消えること |
| B | 「何を言いたかったか」と「どこが誤りか」を分けて出力させる | 意味が通るからと見逃すこと |
| C | 最小限の添削文と、場面に合った自然な文を分ける。画面の添削文は**確定したタグだけを原文に適用してコードが作る** | 添削と推敲が混ざって誤用がぼやけること、確定していない修正が添削文に混ざること |
| D | **タグの引用が原文に一字一句あるかをコードが検証。** 同じ文字列（例：「を」）が複数回出る場合は、文脈フィールドと差分から位置をコードが決め、それでも曖昧なら警告 | すでに直した形で引用すること、繰り返される助詞の誤り 2 件が 1 件にまとめられること |
| E | **原文→添削文で変わった文字がすべてタグで覆われているかを検証** | 黙って直すこと（画面に警告を表示） |
| E2 | **一つのタグの中で別々の語が 2 つ以上直されていないか検出**（`友達を合って→友達に会って`） | ある誤用が別の誤用に埋もれること |
| F | 誤用を仕込んだ評価セットで検出率を測定 | 「よく拾える」を数字にすること |

逆方向の失敗（過剰添削）も測ります。誤用のない答えにタグが何個つくかです。なお句読点・空白・数字・英字の全角半角の違いだけの修正は誤りとして扱いませんが、半角カタカナ（`ｻｰﾊﾞｰ→サーバー`）は実際の表記の誤りとして残します。

日本語に関する知識は [coach/lang_ja.py](coach/lang_ja.py) だけに置き、外には 2 つの関数しか出しません。`tokenize_chunks`（SudachiPy があれば形態素解析、なければ表記ベースの近似）と `non_error_diff` です。[coach/verify.py](coach/verify.py)、多数決、集計は日本語を一切知りません。

### 3. 揺れは temperature ではなく多数決で

同じ答えを 3 回採点し、同じ種別かつ位置が重なる指摘が 2 回以上出たものだけを**確定**とします。1 回だけのものは「参考（確信度低）」として画面に出すだけで、集計には入れません。まとめ画面では種別ごとに、全会一致の件数と確信度が低く除外した件数も表示します。まとめるのはコードです。答え全体を見せる固定 few-shot は入れません（主題と種別が偏るため）。種別ごとに課題と無関係な短い対比ペアを 1 つだけ置いています。

### 4. 2 つのモード（文法 / 表現）

一度に選ぶ種別を減らすと一致率が上がります。選んだモード外の誤用は `OUT_OF_MODE` とだけタグ付けし、順位からは外します。

| 文法モード（形態・統語：正確さ） | 共通 | 表現モード（語彙・語用：適切さ） |
|---|---|---|
| 助詞 / 活用 / テンス・アスペクト / 態・授受・自他動詞 / 接続 | 表記・誤字・変換ミス / その他 | 敬語・丁寧体 / 文体・場面適合 / 文末表現 / 連語・慣用 / 語彙選択 / 文章構成・談話 |

すべてのタグに「韓国語直訳の干渉」フラグが付きます。課題には媒体（メール / チャット / 口頭）と相手との関係（社外 / 上司 / 同僚 / 友人）が設定され、判定はその場面を基準に行います。

## 再現性・検出率のミニ実験

**方法** ([experiments/repro.py](experiments/repro.py))
- 評価セット：誤用を仕込んだ答え 12 件（文法モード 6、表現モード 6、うち誤用なし 2）。韓国語母語話者に典型的な誤り（`友達を合う`、`薬を食べる`、`ストレスを受ける`、`勉強しました時` など）と正解位置を対にしています。
- 3 条件をそれぞれ 3 回採点：**plain**（種別名のみの単純な指示）/ **guide**（詳細な指針プロンプト、1 回）/ **vote**（指針＋3 回多数決）。
- モデルは `gpt-5.6-terra`（reasoning effort = low）。1 回の実験で API 呼び出し 180 回。指標はすべてコードが計算します。

**結果 2 — プロンプト p1・分類表 v1**（`experiments/results/repro_20260920_032338.json`）

| 条件 | モード | 完全一致 | Jaccard | 位置の検出率 | 位置＋種別 | 誤用なしの答えへのタグ | 想定外のタグ |
|---|---|---|---|---|---|---|---|
| plain | 文法 | 0.67 | 0.83 | 1.00 | 0.29 | 0.00 | 0.60 |
| plain | 表現 | 0.17 | 0.67 | 0.93 | 0.67 | 2.33 | 0.80 |
| guide | 文法 | 0.67 | 0.86 | **1.00** | 0.62 | 0.00 | 0.07 |
| guide | 表現 | 0.50 | 0.69 | 0.81 | 0.78 | 0.67 | 0.13 |
| vote | 文法 | 0.67 | 0.85 | **1.00** | 0.58 | 0.00 | 0.07 |
| vote | 表現 | 0.67 | 0.82 | 0.74 | 0.67 | 1.00 | 0.20 |

この表は、語単位の E2 検出と全角半角ルールの限定より前の数値です。当時の結果ファイルにはモデルの生応答が残っていないため再計算できません（生応答の保存はその後に追加。以降の実験は `--rescore` で API なしに測り直せます）。1 回目（p0・分類表 v0）の結果は `experiments/results/repro_20260920_031543.json` にあります。両方の表と詳しい分析は [README_kr.md](README_kr.md) を参照してください。

**現在の状態：** アプリはプロンプト p2・スキーマ s2 で動いています（繰り返し出る引用の位置決定、確定タグからの添削文生成 — [ADR 0009](docs/adr/0009-quote-resolution-version-filter.md)）。実 API での動作確認は 1 件で済ませ、p2 の本実験は評価セットを実際の翻訳で作り直すまで保留しています（[ADR 0007](docs/adr/0007-eval-set-from-user-translations.md)）。下のコストは p1 の実測で、p2 の確認では採点 1 回あたり約 $0.04 でした（文脈フィールドと推論トークンの増加）。

**実験でわかったこと**
1. **プロンプトの規則は守られませんでした。**「タグを分けること」は 3 回中 1 回しか守られず、「半角 `!?` は誤りではない」はほぼ無視されました。どちらもコードの検証（E2 と半角・全角フィルタ）に移しました。「お願いせずコードで防ぐ」という本プロジェクトの方針を、実験が裏づけた形です。
2. こちら側の誤りも 2 つ見つかりました。分類表の優先順位が逆で連語の誤りが語彙選択に入っていたこと、評価セットの正解ラベルが 1 件誤っていたことです。
3. 新しい「引きずられ」の経路も見つかりました。`その→あの` では最小限の添削では見逃し、自然な文のほうだけで黙って直していました。これはまだ塞げていません。

**結論（12 件という小さな標本での話）**
1. **文法モードでは引きずられません。** p1 では guide・vote とも仕込んだ誤用の位置をすべて検出しました（1.00）。p0 では guide 0.96、vote 1.00 です。表現モードは p1 で plain 0.93 / guide 0.81 / vote 0.74 と文法モードより低く、指針を足すほどかえって下がりました（想定外のタグが減った代償と見られます）。LLM は表層的な添削に強く語用論に弱いという先行研究と同じ方向です。
2. **詳細な指針プロンプトは明確に有効です**（同じ実行内での比較、全体）。p1 で plain → guide にすると、種別まで一致した割合 0.49 → 0.71、想定外のタグ 0.70 → 0.10、誤用なしの答えへのタグ 1.17 → 0.33。p0 でも同じ方向です（0.49 → 0.67、0.97 → 0.27、1.33 → 0.50）。
3. **3 回多数決の効果はこの標本では判断できません。** 12 件では 0.1 程度の差は誤差の範囲です。タグごとに「3 回中 2 回」という確信度を示せるため、既定値としては維持しています。
4. **再現性はまだ低いです**（完全一致 0.5〜0.67）。位置は安定していて、種別名が境界で揺れます。

**限界**
- 評価セットは Claude が作成し、GPT が採点しました。モデルは別ですが**人間による正解ではありません**（実際にラベル誤りが 1 件見つかりました）。日本語母語話者による正解の検証が、最も安価な改善策です。
- 「上位 5 種別」は「出題された課題の中でよく間違えた種別」です。主題によって誘発される誤用が異なります。

## 実行方法

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
copy .env.example .env        # OPENAI_API_KEY（または GEMINI_API_KEY と LLM_PROVIDER=gemini）を記入
.venv\Scripts\streamlit run app.py
```

- 練習タブ：サイドバーでモードと主題を選ぶ → 課題を受け取る → 日本語で書く → 採点
- まとめタブ：モードごとの「よく間違える種別 上位 5 件」と実例。デモ用の例（`samples/`）と自分の記録（`data/`）を選べます。
- 連続使用日数の表示はサイドバーで切り替えられます（既定はオフ）。ノルマや目標点はありません。
- 同梱のデモ用サンプルはプロンプト p1 で作ったもので、既定（厳格）のバージョンフィルタではまとめに表示されません。サイドバーの **「이전 버전 기록도 포함」**（以前のバージョンの記録も含める）をオンにすると表示されます。

```powershell
.venv\Scripts\python -m pytest -q                    # 検証・多数決・集計のテスト（API 不要）
.venv\Scripts\python -m experiments.repro            # 実験（API 約 180 回）
.venv\Scripts\python -m experiments.build_samples    # デモ用サンプルの再生成
.venv\Scripts\python -m tools.screenshots            # README 用スクリーンショットの再生成
```

## 構成

```
app.py                  Streamlit 画面
coach/taxonomy.py       誤用分類表 v1（並び順 = 優先順位）
coach/prompts.py        出題・採点プロンプト
coach/llm.py            LLM 呼び出しはここだけ
coach/verify.py         引きずられない検証 D・E・E2（言語非依存）
coach/lang_ja.py        日本語層：語の切り出し、誤りでない差分の判定
coach/voting.py         3 回採点の多数決
coach/stats.py          集計（純粋関数）
experiments/            評価セット、実験スクリプト、結果（モデルの生応答も保存）
docs/adr/               設計決定の記録
samples/                デモ用サンプル（合成、コミット対象）
data/                   自分の記録 JSONL（git 対象外、追記のみ）
```

## 次にやること

- 自然な文のほうだけで黙って直された箇所（例：`その→あの`）を表に出す
- 評価セットを利用者の実際の翻訳から作り直す。誤字か思い込みかを本人が判定し、母語話者が検証、30 件以上へ（[ADR 0007](docs/adr/0007-eval-set-from-user-translations.md)）
- 記録がたまったら、同じ種別の過去事例を検索して例示に使う動的 few-shot
- 今回の範囲外：音声入力、定期テスト、復習スケジューラ、複数のグラフ、ログイン、デプロイ
  - 音声入力は、学習者の誤りを言語モデルで「直して」しまわない認識方式でなければ意味がありません
